## Artifact paths are now portable

Every `ml_training_run.artifact_path` written from this point on is
relative (`ml_artifacts/<file>`), resolved against `ml_artifacts_io.
ARTIFACT_DIR` at load time (`ml_artifacts_io.resolve_path`), not a literal
absolute filesystem path. The 35 pre-existing rows (trained before this
change) were rewritten the same way on 2026-10-13 — a pure string
normalization, no file moved, no model retrained, no metric changed. A
pre-existing absolute path is still honored if one is ever encountered
(back-compat), so this is not a hard requirement for every row, only the
new default.

**Why this matters:** `ml_training_run.artifact_path` travels inside
`wings_theory.db`. Copying that database to a different machine, drive, or
OS used to carry a dead Windows-specific path (`C:\Users\...`) that could
never resolve anywhere else. It now resolves correctly wherever
`backend/ml_artifacts/` is, on any machine — verified by actually copying
the package to `C:\Temp\claude\wt_deploy_test` (a different path) and
confirming all 5 artifacts still resolved and loaded from there.

## Startup loads; it does not retrain

- `wt/api.py`'s `@app.on_event("startup")` calls `ml_startup.
  validate_artifacts_on_startup()` — load + validate every active artifact,
  roll back once on failure, never retrain.
- `ml_scheduler.start_ml_scheduler()`'s background thread now waits a full
  `TICK_SECONDS` (24h) **before** its first cycle, not after — a restart no
  longer silently retrains every model (previously it did; fixed this
  phase, see `TestStartupNeverRetrains`).
- Two scheduled-retraining loops exist (the legacy Prophet-only
  `depletion.start_prophet_refresh_scheduler` and the registry-aware
  `ml_scheduler.start_ml_scheduler`); both are now gated by
  `ml_scheduler.scheduler_enabled()`.

### `scheduler_enabled()` / automatic retraining

| `WT_ENV` | `WT_ML_SCHEDULER_ENABLED` | Automatic daily retraining |
|---|---|---|
| `production` | unset | **off** (default) |
| anything else | unset | on (today's existing dev/test behavior) |
| any | `1` | on, explicitly |
| any | `0` | off, explicitly |

Training in production happens only through an explicit, authorized
command:

```
POST /console/ml/models/{model_key}/train      # one model, current mode
POST /console/ml/models/{model_key}/promote    # one model, next mode
POST /console/ml/cycle                         # every model, right now
```

all gated behind `needs("inventory.write")`, or from a Python shell:
`ml_training.train_one(conn, model_key, triggered_by="you")` /
`ml_training.train_all(conn, triggered_by="you")`.

## Production never fits/mines fresh in-request

`ml_artifacts_io.fresh_fit_fallback_allowed()` gates every serving path's
"no artifact yet" fallback:

| `WT_ENV` | `WT_ML_ALLOW_FRESH_FIT_FALLBACK` | In-request fresh fit/mine allowed |
|---|---|---|
| `production` | unset | **no** (default) |
| anything else | unset | yes (today's existing dev/test behavior) |
| any | `1` | yes, explicitly |
| any | `0` | no, explicitly |

With no active artifact and the fallback disallowed:
- `anomaly.detect_anomalies` / `detect_consumption_anomalies` /
  `detect_flavor_consumption_anomalies` report `model_source: "unavailable"`
  for the ML layer, but the unconditional rule-based layer (`large_fraction`
  / variance-MAD) still answers — never a crash, never a fabricated score.
- `associations.active_combo_recommendations` reports
  `served_from: "unavailable"` with an empty combo list and an
  `empty_reason`, instead of mining FP-Growth in-process.
- `depletion`'s Prophet path already never fit in-request (falls back to
  the EWMA baseline) — no change needed there.

## Building a deployment package

```
cd backend
python scripts/build_deployment_package.py <target_dir>
```

Produces `<target_dir>/backend/` + `<target_dir>/frontend/` (mirroring the
real repo layout — `wt/api.py` locates `frontend/` by a fixed relative hop
from its own file, so it must stay a sibling of `backend/`), containing:

- `backend/wt/`, `backend/migrations/`, `backend/requirements.txt`,
  `backend/start_server.ps1`
- `backend/wings_theory.db` (WAL-checkpointed before copying, so the single
  file is complete — copying it without checkpointing first was the one bug
  this script's own verification run caught: a stale copy missing the
  latest committed training runs)
- `backend/ml_artifacts/` — **only** the 5 currently-active artifacts, not
  the full training history
- `frontend/` — the static POS/KDS/console/landing assets

Deliberately excluded (reasons recorded in the generated
`DEPLOYMENT_MANIFEST.md`/`.json`): `tests/`, `venv/`, `backups/`, `dev/`,
`wings_theory_demo.db`, `.secret`, `start_server_dev.ps1`, `scripts/`.
Nothing at the source is deleted — this only copies.

## 2026-10-16: shipping artifacts + a sanitized DB snapshot to GitHub

Everything above stayed local (nothing under `backend/ml_artifacts/` or any
`.db` was ever pushed). This phase makes the repo itself deployable: a
fresh `git clone` now has what it needs to boot without training a model
or seeding a database by hand.

**What changed:**

- `backend/ml_artifacts/` is still gitignored *as a directory* (a local
  training run writes a new hash-named file every time — that churn stays
  untracked), but the files the registry currently calls **active** are
  carved back out by exact name in `.gitignore` and committed, tracked via
  Git LFS (`.gitattributes`). `backend/ml_artifacts/MANIFEST.json` records
  each one's `model_key`/`run_id`/`mode`/`schema_version`/sha256.
- `scripts/build_github_deploy_snapshot.py` takes a **consistent** copy of
  `wings_theory.db` via SQLite's online backup API (`sqlite3.Connection.
  backup()` — correct under WAL/concurrent writers, unlike a raw file
  copy), then sanitizes the copy: every `app_user` password is replaced
  with a documented demo credential (`must_change_password=1` set, so
  first login forces a real change) and `auth_session` is cleared. Output:
  `backend/deploy/wings_theory.snapshot.db` (Git LFS) +
  `backend/deploy/SNAPSHOT_MANIFEST.json`. The live source database is
  only ever read, never opened for writing.
- `wt.db.bootstrap_from_snapshot_if_missing()`, called from `api.py`'s
  startup event *before* the first `db.get_conn()`, copies
  `backend/deploy/wings_theory.snapshot.db` into place **only if** the
  configured `WT_DB` path does not already exist. An existing database —
  production, demo, or a prior run's — is never touched.

**Finding reported, not silently patched:** the registry's currently
active `stock_loss_isoforest` run (id 31, `stock_loss_isoforest__
cb9abd10b51a.joblib`) has no artifact file anywhere in the repo or its
backups — it is missing at the source, not just excluded here. (The
artifact this document described on 2026-10-13, `...fb238ca8dbf8.joblib`,
was superseded by a later retrain whose file never made it to disk; see
`backend/deploy/SNAPSHOT_MANIFEST.json`'s `ml_artifacts` list, which marks
it `MISSING_AT_SOURCE` rather than fabricating a replacement.) This is not
a crash: `ml_startup.validate_artifacts_on_startup()` already rolls back
to the previous run for that one model and the rule-based layer serves in
the meantime — exactly the designed degradation path. Retraining
`stock_loss_isoforest` to produce a real replacement file is a separate,
deliberate action (`POST /console/ml/models/stock_loss_isoforest/train`),
not done as part of this packaging work.

**Credentials in the public snapshot:** every account's password hash in
`backend/deploy/wings_theory.snapshot.db` was replaced before it was ever
written to disk under Git's control. The documented demo password is
`WingsTheoryDemo!2026` (see `scripts/build_github_deploy_snapshot.py`'s
`DEMO_PASSWORD`); every account is flagged `must_change_password=1`. No
password hash, session token, or `.secret` JWT-signing key from the real
source database is present anywhere in Git history for this phase.
